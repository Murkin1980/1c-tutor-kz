# MiniBase — Cloudflare backend platform

## Назначение

MiniBase — компактный BaaS для 1C Tutor KZ и будущих небольших проектов.
Платформа предоставляет стабильный прикладной API поверх Cloudflare Workers,
D1 и R2.

Базовый MiniBase развёрнут в production на Cloudflare Worker, поддерживает
provisioning изолированной D1, Data API, R2, аудит и квоты. 1C Tutor использует
MiniBase для прогресса и заметок, сохраняя localStorage как fallback.

Разработка платформы ведётся в отдельной задаче Codex и отдельном репозитории
`Murkin1980/minibase-cloudflare`. Этот файл определяет интеграционный контракт
со стороны 1C Tutor.

## Архитектурные границы

- Cloudflare Worker: control plane и data API;
- отдельная D1-база на проект для физической изоляции данных;
- отдельный префикс или bucket R2 на проект для файлов;
- KV для маршрутизации проекта, отозванных ключей и короткоживущего кэша;
- Durable Objects только при подтверждённой потребности в realtime;
- Pages для панели владельца;
- никаких секретных ключей в браузерном bundle.

## Ключи и сессии

1. `mb_publishable_*` — публичный project key. Допустим во frontend закрытого
   пилота и имеет только `data:read,data:write`.
2. Доступ к приложению single-owner пилота ограничивается Cloudflare Access.
3. `mb_secret_*` — серверный ключ проекта. Никогда не передаётся браузеру.
4. `mb_management_*` — ключ control plane для создания баз, применения миграций,
   ротации ключей и экспорта. Хранится только как Cloudflare Secret.

Ключи имеют scope, срок действия, ротацию, отзыв и аудит. В базе хранится только
необратимый хэш секретной части. Полное значение показывается владельцу один раз.

### Текущее ограничение интеграции

Production-версия MiniBase принимает project keys и не выдаёт отдельные сессии
конечных пользователей. Поэтому текущая интеграция разрешена только для
закрытого single-owner пилота за Cloudflare Access.

Frontend 1C Tutor:

- принимает только `VITE_MINIBASE_URL` и `VITE_MINIBASE_PUBLISHABLE_KEY`;
- отклоняет secret и management keys;
- сохраняет локальный fallback;
- синхронизирует `tutor_progress/owner` и `tutor_notes/lesson_<lessonId>`;
- не поддерживает публичный multi-user режим.

Утраченный management key отозван и заменён. Раскрытый во время onboarding
project secret также отозван и заменён; frontend его никогда не использовал.

### Пользовательская сессия frontend

При демо-входе frontend обменивает `mb_publishable_*` на восьмичасовой
`mb_session_*` через `POST /v1/sessions/exchange`. Запрос отправляется с
`credentials: include`, чтобы Cloudflare Access мог подтвердить разрешённый
email. Сессионный токен хранится только в `sessionStorage`, автоматически
используется Data API и удаляется до best-effort запроса
`DELETE /v1/sessions/current` при выходе.

Если Access недоступен, вернул страницу входа вместо JSON или сеть не отвечает,
демо-вход продолжает работу в локальном режиме. `localStorage` остаётся fallback
для учебного прогресса, но сессионный токен туда никогда не записывается.

## Автоматическое создание проекта

```text
POST /v1/projects
Idempotency-Key: <uuid>
Authorization: Bearer mb_management_...
```

Control plane создаёт запись проекта, изолированную D1-базу через Cloudflare API,
применяет версионированные миграции, настраивает файловое пространство, выпускает
ключи и записывает аудит. При частичной ошибке проект получает состояние
`provisioning_failed`, а операцию можно безопасно повторить.

Cloudflare API token доступен только control plane и никогда не выдаётся
клиентскому приложению.

## История решения

Внешний BaaS отклонён как избыточный для внутреннего single-owner проекта;
выбрана собственная платформа MiniBase Cloudflare. Приложение работает через
repository interfaces, а не вызывает backend непосредственно из экранов.

## Этапы

- MB0: ADR, threat model и API-контракт;
- MB1: проекты, ключи и аудит;
- MB2: автоматический provisioning D1 и миграции;
- MB3: Auth и CRUD data API;
- MB4: R2 Storage и квоты;
- MB5: backup и проверяемое восстановление;
- MB6: пилот второго проекта, backup и восстановление;
- MB7: решение о самостоятельном публичном продукте.

## Стоп-критерии

- management или secret key попадает во frontend;
- нет ротации, отзыва или аудита ключей;
- данные проектов смешиваются без подтверждённой необходимости;
- миграция не имеет контрольных сумм и плана возврата;
- резервная копия не прошла тестовое восстановление;
- требуется платный компонент без решения владельца.
